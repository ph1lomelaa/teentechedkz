# Аудит готовности к продакшену — TeenTechEd CRM

Дата: 2026-07-22. Проведён тремя параллельными независимыми аудитами (backend security/architecture, frontend logic/architecture, design-system consistency). Ниже — сведённый отчёт с конкретными файлами и строками.

## Вердикт

**Не готово к запуску.** Не из-за дизайна (это чинится) — из-за авторизации в бэкенде. Сейчас минимум 8 эндпоинтов либо вообще без проверки доступа, либо с проверкой, которая не делает того, что должна. Один из багов (#1) даёт **любому ментору** возможность выдать себе роль admin одним запросом. Это надо закрыть до какого-либо публичного запуска, счёт на часы, не на "как-нибудь потом".

Дизайн-фрагментация ("каждая кнопка — свой мир") подтвердилась и оказалась хуже, чем кажется на глаз: это не 2 системы (старая/новая), а **7 параллельных кнопочных реализаций** одновременно в проде.

## 1. КРИТИЧНО — исправить до запуска (эскалация привилегий, утечка данных)

Модель доступа: есть `mentor_scope.require_student_access()` — правильный паттерн, применён в `roadmaps.py`, `meetings.py`, `credentials.py`, большей части `documents.py`/`chat.py`. Но добрая половина эндпоинтов, работающих со student_id, либо не вызывает его вовсе, либо проверка — no-op. Портальный студенческий аккаунт технически может достучаться до back-office данных.

1. **Повышение до admin через `/users`** — `backend/app/core/deps.py:66`, `backend/app/api/v1/endpoints/users.py:42,77,146,169-171`
   `AdminOrMZK` включает роль `mentor`. Через неё гейтятся `POST /users` (создание пользователя с произвольной ролью), `PATCH /users/{id}` (смена роли любого пользователя). Guard на self-demotion (строка 169) блокирует только смену *на другую* роль, не блокирует **повышение себя до admin**. Любой ментор → полный админ одним запросом.

2. **Самоназначение ментором к любому студенту** — `backend/app/api/v1/endpoints/mentor_assignments.py:23-70`
   `POST /mentor-assignments/student/{id}/self` вообще без проверки роли — доступно и студенческому аккаунту. Через это можно назначить себя lead-ментором любого студента и получить полный mentor-scope доступ (roadmaps, встречи, credentials, чат, документы) к чужой карточке.
   *Статус: пользователь сказал оставить самоназначение как фичу для менторов ("пусть остаётся") — уточняем только объём: должно ли это остаться открытым буквально для любого авторизованного пользователя (включая студенческие аккаунты), или сама фича должна остаться, но ограничиться staff-ролями. См. вопрос ниже.*

3. **Выгрузка всей базы студентов без авторизации** — `backend/app/api/v1/endpoints/export.py:20-109`
   `GET /export/students` и `/export/students/{id}` — без проверки роли вообще. Любой авторизованный (включая студента) может выгрузить XLSX со всей базой: контакты, финансы, контракты.

4. **Guardians (родители, включая ИИН) без авторизации** — `backend/app/api/v1/endpoints/guardians.py:23-133`
   Список/создание/изменение/удаление guardian-записей без role- и scope-проверки. Любой студент может править/удалять записи опекунов (включая зашифрованный ИИН) любого другого студента.

5. **`portfolio.py:102-103`** — `_check_access()` буквально `pass`, комментарий врёт, что доступ проверяется в другом месте. Открыто всем для любого student_id.

6. **`confidential_notes.py:17-95`** — нет scope-проверки; хуже — `note_visible_to_role()` для роли `student` фолбэчится на `visibility == all_mentors`, т.е. **студент может читать конфиденциальные заметки о любом студенте**, а не только о себе. Создание/удаление заметок тоже без проверки владельца.

7. **`communication.py:31-204`** — логи коммуникации и pending AI-инсайты читаются/одобряются без scope-проверки. Любой студент может approve/reject чужой AI-инсайт — approve тихо пишет изменения в профиль студента.
   *Уточнение от пользователя:* чтение логов может оставаться в рамках общей CRM-базы (см. п.1), но **approve/reject должен быть действием конкретного ментора в его личном кабинете** — то есть здесь всё равно нужен минимум role-check (staff-only), а в идеале scope к ответственному ментору, а не полностью открытый эндпоинт.

8. **`contracts.py:24-51,92-105`** — `create_contract` вообще без проверки доступа; можно сфабриковать контракт на любого студента.

**Общая причина**: `require_roles`/`_require_admin_mzk` и `mentor_scope.require_student_access` — два разных guard'а, и на десятке эндпоинтов вызван только первый (или не вызван никакой). Нужен systematic pass по всем student-linked эндпоинтам с чек-листом "role check + ownership check", а лучше — тест на матрицу доступа (роль × эндпоинт × чужой/свой student_id), чтобы это не всплыло снова после рефакторинга.

## 2. ВЫСОКИЙ приоритет

**Backend:**
- **`applications.py:19-22`** — `_can_edit()` возвращает `True` для любого mentor до проверки `mentor_ids` — scope-проверка мертвый код. `delete_application` вообще без неё.
- **`documents.py:196-282`** — `verify_document`/`delete_document` без `require_student_access` (хотя соседние `set_visibility`/`set_document_type` в этом же файле её вызывают — несогласованность внутри одного файла). Любой ментор может удалить документы чужого студента.
- **`guardians.py:34-57`** — `reveal_iin` без scope-проверки: любой ментор может раскрыть незамаскированный ИИН опекуна любого студента.
- **`students.py:420-755`** — N+1: до ~13 последовательных запросов на студента внутри списочного эндпоинта, `size` управляется клиентом до 2000 — одна страница = десятки тысяч round-trip'ов к БД. Риск для латентности/доступности под нагрузкой.
- **`status_history.py`, `services.py`** — role-check есть, mentor-scope нет: любой ментор видит историю изменений/сервисы по всем студентам компании, не только своим.
- ~~`students.py:1097` — "role не граница доступа для списка студентов"~~ — **подтверждено пользователем как осознанное продуктовое решение, не баг.** CRM — общая база, все staff-роли намеренно видят всех студентов. Не трогаем.
- **`integrations.py:11-19`** — эндпоинт токена Deepgram отдаёт в браузер сырой постоянный `DEEPGRAM_API_KEY` вместо короткоживущего скоупнутого токена.

**Frontend:**
- **`ChatThread.tsx:71-82`** (`send()`) — нет `catch`, только `finally`. Сбой отправки (сеть/500) — сообщение молча исчезает, юзер не узнаёт, что не отправилось. Компонент общий для чата портала и воркспейса — это главный чат-канал во всём приложении.
- **`lib/ws.ts:47-53`** — реконнект каждые фиксированные 3с без backoff и лимита попыток. При падении бэкенда каждая открытая вкладка (чат + уведомления) будет долбить `/api/v1/ws` бесконечно. `useDeepgramTranscription.ts` рядом делает это правильно (экспоненциальный backoff, MAX_RECONNECT_ATTEMPTS) — стоит унифицировать.
- **`WorkspaceChatPage.tsx:151-168`** — гонка двух `useEffect`: при переходе по диплинку "открыть чат со студентом X" второй эффект может молча выбрать не тот чат (`items[0]` вместо запрошенного `requestedStudentId`), если `items` ещё пустой на момент первого рендера.

## 3. СРЕДНИЙ приоритет

**Backend:**
- `public.py:33-76` — публичная форма заявки без rate-limit (в отличие от соседнего `mentor-signup` в том же файле) — можно заспамить `intake_submissions`.
- `telegram_webhook.py:21-23` — проверка secret token пропускается целиком, если `TELEGRAM_WEBHOOK_SECRET` не задан в env — если забыть выставить в проде, вебхук примет неаутентифицированные апдейты.
- `main.py:15-30` — дефолтные секреты (`JWT_SECRET_KEY`, `PGCRYPTO_KEY`, `FIRST_ADMIN_PASSWORD`, `MINIO_SECRET_KEY`) в проде только логируются как CRITICAL, но не блокируют запуск — если логи не мониторятся, приложение может месяцами работать с подделываемым JWT.
- `chat.py:634` — JWT токен передаётся в query string WebSocket URL — оседает в логах прокси/истории браузера, в отличие от Authorization-header паттерна везде остальном.
- `mentor_assignments.py:98-148` — create/update/delete assignment через `_require_admin_mzk`, который тоже включает `mentor` — любой ментор может менять чужие назначения ментор↔студент.

**Frontend:**
- `WorkspaceChatPage.tsx:465-480` — поиск в чате без debounce, каждое нажатие клавиши — новый запрос.
- `ChatThread.tsx` без `key` на смене `conversationId` — старые сообщения на миг остаются под новым заголовком чата.
- `NoteDetailPage.tsx:111-122` — правки в заметке молча затираются при рефетче (нет dirty-tracking); риск при мультивкладочной работе с одной заметкой.
- Несогласованный UX ошибок: `alert()` вместо toast в `PortalDocumentsPage.tsx`, `StudentsListPage.tsx:1111`; `window.confirm()` вместо стилизованного Dialog в 7 местах, хотя паттерн диалога-подтверждения уже есть (`NoteDetailPage.tsx:252-276`).

Подтверждено и оказалось серьёзнее, чем один старый/новый набор компонентов. В проде параллельно живут **7 разных кнопочных реализаций**:

Дополнительно подтверждено:
- **18 разных произвольных значений radius** (`rounded-[2px]` … `rounded-[24px]`) плюс 7 именованных классов вперемешку для визуально одной и той же "карточки".
- **9 разных значений padding** на бордер-панелях одной и той же формы.
- **43 файла** используют сырые Tailwind-цвета (`bg-red-500`, `text-gray-400`) вместо токенов — это "спасает" большой compatibility-layer в `index.css:265-370`, который форсит переопределение этих классов внутри `.crm-shell`/`.workspace-shell`/`.portal`. Сам факт существования такого слоя — это симптом проблемы, а не решение: он патчит последствия вместо того, чтобы файлы использовали токены.

## 6. Диагностика по новым задачам (2026-07-22) — результаты и план фикса

Самоназначение ментором (п.3) решено: ограничиваем staff-ролями (admin/mzk_manager/mentor), фичу свободного самоназначения без approval оставляем как есть для сотрудников. Входит в Фазу 0.

### 6.1 Telegram-бот "не подключается"

Корневых причин может быть несколько одновременно, ни одна не проверяется автоматически и не алертит:

- **Самый вероятный сценарий**: на проде не задан `TELEGRAM_BOT_TOKEN`/`TELEGRAM_WEBHOOK_URL`, либо задан неверно — и это проходит вообще без единой строчки в логе (`main.py:39` — в отличие от sheets/notion sync рядом, здесь нет `else: logger.info("disabled")`).
- **Регистрация webhook — одноразовая, без ретрая.** Происходит один раз при старте процесса (`main.py:44-51`); если в этот момент сеть/DNS ещё не готовы — бот остаётся незарегистрированным до ручного рестарта контейнера. `webhook_health_loop` (`telegram_bot.py:552-576`) раз в 10 минут ПРОВЕРЯЕТ рассинхрон и ЛОГИРУЕТ warning, но **не переregистрирует** — то есть свой же диагностический код уже умеет обнаруживать поломку, просто чинить её не запрограммирован.
- **Вероятная практическая причина**: Telegram Privacy Mode не отключён через BotFather — тогда бот добавлен в группу, но не получает обычные сообщения (только команды/упоминания). В коде уже есть готовый диагностический эндпоинт для этого: `GET /telegram-chats/{chat_id}/readiness` (`telegram_chats.py:1289-1358`) — проверяет именно privacy_mode и права админа. Это можно проверить прямо сейчас без доступа к серверу.
- **Инсайты не генерируются — отдельная и куда более тихая причина**: если не задан `OPENAI_API_KEY`/`ANTHROPIC_API_KEY`, `telegram_extraction.py:62-64` просто пишет `INFO`-лог "No AI provider configured" на каждое сообщение и выходит — без уведомления админу, без индикатора в UI. Это самый вероятный "тихий" виновник.
- Дополнительно: извлечение инсайта идёт **синхронно внутри HTTP-запроса вебхука** (`telegram_bot.py:543-546`, до `db.commit()`) — если AI-вызов подвисает, это может деградировать сам вебхук и выглядеть как "бот отваливается".
- Есть и more banal причины: чат может быть непривязан (`unbound` — сообщения не сохраняются вообще) или стоять на паузе ИИ (кнопка "Пауза AI" в инбоксе) — тогда сообщения видны, а инсайтов нет по замыслу.

**Фейковый чат "Жасмин"** — не найден в коде вообще (проверено везде: seed-скрипты, фронтенд, миграции). Это реальная запись в проде, оставшаяся от тестирования. Чинится не кодом, а SQL-запросом на проде (`SELECT ... FROM telegram_chats WHERE title ILIKE '%жасмин%'`) — либо кнопкой "Закрыть чат" в самом инбоксе, если запись не критично удалять полностью.

**Что нужно исправить в коде** (независимо от прод-конфига):
1. Добавить `else: logger.warning(...)` при отсутствии `TELEGRAM_BOT_TOKEN`/`WEBHOOK_URL` — чтобы поломка была видна в логах сразу.
2. Научить `webhook_health_loop` не просто логировать рассинхрон, а **сам переregистрировать** webhook.
3. Поднять уровень лога "нет AI-провайдера" с `INFO` до `WARNING`/`ERROR` + создавать admin-уведомление (как уже сделано для webhook-фейла) — иначе это будет ломаться тихо снова и снова.
4. Вынести AI-извлечение инсайта из синхронного пути обработки вебхука в фоновую задачу — чтобы медленный/зависший AI-вызов не бил по доставке сообщений.

### 6.2 Конспекты — не долетают в "формате для ученика"

Ключевая находка: **"публикация ученику" не создаёт отдельную версию текста под студента — она просто показывает тот же текст, что и ментору**, с опциональной возможностью скрыть целые блоки. Промпт для AI прямо говорит "пиши для менеджера, а не для машины" (`student_notes.py`/`note_sessions.py`) — то есть контент по умолчанию написан для ментора, не для ученика.

Дополнительно:
- После недавнего фикса ("Bug #5") заметка **автопубликуется студенту сразу при апруве** ментором — без обязательного шага кураторства. Значит первая же одобренная заметка может улететь ученику с внутренней формулировкой AI как есть.
- Эвристический fallback (когда нет AI-ключа) физически не может скрывать блоки по отдельности — весь текст, включая секцию "Контекст для менеджера", попадает в один нераздельный блок (в разметке используется `**bold**`, а не `##`-заголовки, которые единственные распознаются как границы блоков).
- Внутренние QA-предупреждения ("Требует проверки качества") вклеиваются прямо в текст блока и не могут быть скрыты отдельно от него — риск утечки внутренней пометки студенту.
- **Нет уведомления студенту** о новом конспекте вообще — ни в БД, ни в UI. Студент узнаёт только если сам зайдёт в "Конспекты".
- Восстановление транскрипта при сбое записи — полностью ручное действие, easy to forget; сам процесс "Завершить" не детектирует частично пропущенный кусок записи.

**Что нужно исправить:**
1. Убрать автопубликацию без ревью ИЛИ явно предупреждать ментора при апруве, что контент уйдёт студенту как есть — нужно ваше решение, какой вариант нужен.
2. Добавить в промпт/пайплайн реальный student-facing rewrite (не просто скрытие блоков) — либо отдельный AI-шаг "перепиши для ученика проще", либо строгий шаблон с явными `##`-секциями, часть из которых по умолчанию скрыта от студента.
3. Поднять QA-предупреждения в отдельное, всегда скрытое от студента поле (не вклеивать текстом в блок).
4. Добавить `Notification` при публикации заметки студенту (по аналогии с уведомлением о переносе встречи).
5. Чинить структуру эвристического fallback — использовать `##`-заголовки для каждой секции, чтобы `hidden_blocks` реально работал.

### 6.3 Инсайты/заметки — почему не всегда попадают во все три места

Корневая причина, буквально структурная: **`PendingInsight` (из Telegram) и `StudentNote` (из конспектов) — две никак не связанные таблицы**, нет FK между ними. А ещё есть 4 разных пути создания заметки, и только 2 из них корректно проставляют публикацию студенту:

| Источник | → Профиль ученика | → Личный кабинет ментора | → Общая CRM |
|---|---|---|---|
| Telegram-инсайт (структурный) | Работает для 8 из 14 полей — **6 полей вообще никогда не показываются в портале** (gpa, achievements_text, budget_per_year, transcript_resume_url, group_direction, additional_sphere), хотя запись в них идёт | Только через общую страницу `/workspace/status` (по умолчанию не отфильтрована на "мои"), либо мёртвый счётчик на карточке студента без возможности открыть/одобрить | Работает, но без проверки роли (уже в критичных багах, п.7) |
| Telegram-инсайт (контекстный, unmatched) | Создаёт `StudentNote`, но **публикация не проставляется** — заметка "зависает" невидимой | То же | Видна в очереди, но после апрува — никуда |
| Конспект (запись встречи) | Работает, автопубликуется | Работает — отдельная авто-отфильтрованная на "моих" страница `WorkspaceNotesPage` | Работает |
| "Разбор истории чата" из `telegram_chats.py` | Работает, автопубликуется | Не в очереди (применяется сразу) | Не в очереди (сразу approved) |
| "Разбор истории чата" из `workspace.py` (unified) | **Публикация не проставляется — баг**, тот же класс, что и выше | Не в очереди | Не в очереди |

То есть у вас на самом деле не "недоделанная фича", а **два бага одного типа** (пропущенный `published_to_student=True` в двух из четырёх мест, где его уже поставили в двух других — это забыли при том же самом фиксе "Bug #5"), плюс архитектурный разрыв между Telegram-инсайтами и конспектами, из-за которого у ментора нет единой персональной очереди "то, что мне нужно проверить" — Telegram-инсайты туда просто не попадают.

**Что нужно исправить:**
1. Проставить `published_to_student=True`/`published_at`/`published_by` в `communication.py:180-200` и `workspace.py:1625-1638` — двухстрочный фикс в двух местах, устраняет "невидимые" заметки.
2. Добавить 6 отсутствующих полей в `portal.py:82-106` (portal_profile) и на страницу профиля студента — либо осознанно решить, что часть полей внутренние (тогда не давать их писать через approve-flow, который бьёт в student-facing профиль).
3. Дать мотнору персональную очередь, которая реально объединяет оба источника (Telegram-инсайты + конспект-драфты) — либо связать `PendingInsight`↔`StudentNote`, либо хотя бы завести единый "мои задачи на ревью" вьюху, использующую оба источника с фильтром на назначенного/ответственного ментора.

### 6.4 Навигация по чатам/конспектам в CRM

Раз доступ к CRM намеренно общий (см. п.1) — навигация должна быть рассчитана на "быстро найти любого из многих студентов", а сейчас:

- **У чата вообще нет поиска/фильтра по списку бесед** — поиск есть только внутри уже открытого диалога.
- Список чатов сортируется по дате обновления, не "непрочитанные сверху"; в боковом меню у пункта "Чат" нет бейджа непрочитанных (в отличие от "Уведомлений").
- Даже у admin/mzk_manager по умолчанию фильтр "только мои студенты" (`useWorkspaceScope.ts`) — переключатель на "показать всех" технически существует в коде (`setMentorFilter`), но **нигде не подключён к UI** — реально им нельзя воспользоваться.
- Конспекты и чат физически не связаны: со страницы конспекта нет перехода в чат этого студента и наоборот; вкладка "Заметки" на карточке студента — это вообще другая фича (конфиденциальные заметки), не конспекты — тот же ярлык, разный смысл, легко запутаться.
- CRM-версия заметок с нормальным поиском (`/notes`, с фильтрами по имени/ответственному) не подключена к навигации воркспейса вообще — реально используется урезанная `WorkspaceNotesPage` с одним select-дропдауном вместо поиска.
- Глобального поиска (по студентам/чатам/конспектам сразу) нет вообще.

**Что нужно исправить:**
1. Добавить поиск/фильтр по списку бесед в `WorkspaceChatPage` (по имени студента).
2. Сортировка "непрочитанные сверху" + бейдж непрочитанных в нав-меню.
3. Починить переключатель "мои/все студенты" — подключить к UI (сейчас код есть, кнопки нет).
4. Связать конспекты и чат: ссылка на чат студента со страницы его конспекта и обратно.
5. Переосмыслить `WorkspaceNotesPage` — либо добавить туда полноценный поиск как в `/notes`, либо просто подключить `/notes` в навигацию воркспейса вместо урезанной версии.
