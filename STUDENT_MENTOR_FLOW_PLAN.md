# План инкремента: интерактив студента ↔ ревью ментора

**Автор:** Aziza · **Дата:** 2026-07-25 · **Зона ответственности:** student–mentor interaction (фронт + бек этого домена). Админка — вне скоупа (второй разработчик).

---

## 1. Проблема и цели

Сейчас портал студента — витрина: бекенд жёстко запрещает студенту менять статус задач (`roadmaps.py`, комментарий «Roadmap is mentor-managed end to end»), при этом фронт до сих пор рисует кликабельные чекбоксы, клик по которым **молча падает с 403** (в мутации нет даже `onError`). Модульный докстринг `roadmaps.py` противоречит собственным guard'ам. Это и есть «inconsistency»: UI обещает интерактив, логика запрещает.

Цели инкремента:

1. **Студент интерактит**: отмечает задачи своего roadmap, прогресс (жёлтая дорожка) двигается мгновенно — геймификация удерживает вовлечённость.
2. **Ментор не теряет контроль**: каждая отметка студента — событие ментору; ментор фиксирует (подтверждает) или возвращает с комментарием.
3. **Одно консистентное состояние**: ни мёртвых чекбоксов, ни тихих 403; правила бекенда = возможности UI.
4. **Отчёты не врут**: «done» в дашбордах/CRM всегда значит «подтверждено ментором».

## 2. Ключевое решение: две оси вместо одной

Рассматривались три архитектуры (мгновенный done + ревью-оверлей; двухосевая модель; минимальный дифф). После адверсариального разбора выбрана **двухосевая модель** — единственная, где:
- «done» честен во всех отчётах **по построению** (воркспейс-дашборды считают `status='done'`, и это не меняет смысла);
- нет «отпразновали → отобрали»: празднование этапа срабатывает только на подтверждённом;
- конкурентные операции (студент снял отметку ↔ ментор подтверждает) решаются блокировкой строки (`with_for_update` — устоявшийся паттерн этого кода).

**Модель:** `status` (`planned|in_progress|done`) остаётся канонической истиной ментора. Заявка студента живёт в новой ортогональной колонке `review_status: none|pending|approved|returned` + штампы `completed_by/at`, `reviewed_by/at`, `review_comment`. Прецедент в кодовой базе — жизненный цикл анкет (`draft→sent→submitted→reviewed`).

**Сабтаски** — свободный микропрогресс студента: тогглятся без ревью (но с аудитом), никогда не автозакрывают родительскую задачу. Когда последняя сабтаска готова — фронтовый нажим: «Все подзадачи готовы — отметить задачу выполненной?».

## 3. State machine (сервер энфорсит)

| # | Переход | Актор | Guard | Эффекты |
|---|---|---|---|---|
| T1 | заявка «сделано» | студент | свой roadmap (иначе 404), roadmap активен (409 `ROADMAP_ARCHIVED`), `audience==applicant` (403), `status!=done` (409 `ALREADY_DONE`); повторная заявка — идемпотентный no-op | `review_status=pending`, `completed_by/at`; `log_change`; нотификация ментору |
| T2 | снятие заявки | студент | только пока `pending` (409 `NOT_PENDING`) | `review_status=none`, очистка `completed_*`; удалить **непрочитанную** нотификацию ментора по ключу `kind+task_id` (не по link — иначе снесёт уведомления о других задачах студента) |
| T3 | подтвердить | staff | `pending` + **`with_for_update`** (иначе 409 `ALREADY_REVIEWED`) | `status=done`, `review_status=approved`, `reviewed_by/at`, комментарий опционален; `log_change` ×2; нотификация студенту |
| T4 | вернуть | staff | как T3 + непустой комментарий (422) | `status=in_progress`, `review_status=returned`, `review_comment`; нотификация студенту (high, комментарий в теле) |
| T5 | неявное ревью | staff через существующий `PATCH /roadmap-tasks/{id}` при `pending` | staff-guard без изменений | новый `status=done` → `approved`; иначе → `none`; штамп `reviewed_by/at`; **нотификация студенту** о судьбе его заявки (дыра всех трёх исходных дизайнов — закрываем); `log_change` на все staff-правки (сегодня staff-правки roadmap вообще не логируются) |
| S1 | тоггл сабтаски | студент | свой roadmap, родитель `audience==applicant`, roadmap активен; whitelist `{is_done}` | флип + `log_change`; без ревью и нотификаций |

`approved` vs `none` у done-задачи различимы намеренно — это аудит-ответ «как задача стала done: студент+подтверждение или ментор внёс сам».

## 4. API

**Новые студенческие эндпоинты** (не ветка в staff-PATCH — эндпоинт заявки не принимает **ни одного поля**, что структурно убивает всю поверхность whitelist-атак, включая подмену `audience`):
- `POST /api/v1/portal/tasks/{id}/complete` → T1. Ответ обогащён: `{task, progress, stage_claimed}` — портал реагирует в кадре клика без рефетча.
- `DELETE /api/v1/portal/tasks/{id}/complete` → T2.
- Студенческая ветка в `PATCH /roadmap-subtasks/{id}` → S1 (та же URL, что уже зовёт фронт).

**Новый менторский**: `POST /api/v1/roadmap-tasks/{id}/review` `{action: approve|return, comment?}` → T3/T4, guard `_assert_staff` (менторы в своём скоупе).

**Чтения**: `GET /workspace/roadmap-tasks` + параметр `review_status` и поля `review_status, completed_at, completed_by_name, reviewed_at, review_comment`; те же поля в `/portal/tasks` и `/portal/roadmap`.

**Coordinator-задачи НЕ фильтруем из портала** (это был бы единственный ломающий пейлоад-чейндж: «куда делись мои задачи», скачки процентов у живых студентов). Вместо этого: сериализуем `audience`, в портале такие строки — read-only без чекбокса.

**Попутные фиксы консистентности**: правка лживого докстринга `roadmaps.py:6-8`; 403 старым кэшам — всегда с `X-Error-Code`.

## 5. События и каналы (ментор не может пропустить)

Новый хелпер `services/notify.py`: `notify(db, ...)` (строка в транзакции вызывающего) + `push_ws(...)` (обёртка над `ws_hub.manager.send_to_users`); порядок как в chat.py: mutate → commit → refresh → WS best-effort.

| kind | кому | заголовок | link | priority |
|---|---|---|---|---|
| `task_review_requested` | ментор | «Студент отметил задачу выполненной» | `/workspace/review` | high |
| `task_approved` | студент | «Ментор подтвердил задачу» | `/portal/tasks` | normal |
| `task_returned` | студент | «Задача возвращена с комментарием» | `/portal/tasks` | high |

Резолв ментора: `roadmap.mentor_id` → fallback `primary_mentor_id()`. **Без ментора**: не веерная рассылка всем админам (шторм колокольчиков), а одна агрегированная строка в день «Заявки студентов без ментора: N» для mzk/admin.

**WS-события** (транспорт готов — `lib/ws.ts` + `useWsEvent`, бек шлёт `message.new`/`notification.new` уже сейчас): `task.review_requested`, `task.review_done`, `roadmap.updated` (генеральный cache-buster — каждая поверхность инвалидирует свои ключи). Колокольчик ментора оживает **без единой строчки фронта** — `NotificationsBell` уже подписан на `notification.new`; добавляем только `refetchInterval: 60_000` как фолбэк без сокета.

**Telegram** (фаза 2): arq-джоба с **коалесингом** — `_job_id='tg-review-{mentor}-{student}'` + `_defer_by=10 мин`, при исполнении перечитывает счётчик pending: буря топлений схлопывается в один пинг «Студент отметил N задач», и джоба само-глохнет, если студент всё снял. Гейт `ENABLE_TASK_REVIEW_TELEGRAM`.

**Дайджест** (фаза 2): луп в воркере по образцу `payment_notifier_loop` — раз в день ментору с pending старше ~4ч: «У вас N задач ждут проверки (M — дольше суток)». Гейт `ENABLE_REVIEW_DIGEST`.

**Аудит**: `log_change` на каждый переход (`source=portal|workspace_review`); история читается существующим `GET /history?entity_type=roadmap_task`.

## 6. UX студента (портал)

Визуальный язык **«одна/две галочки»** как в мессенджерах — мгновенно считывается без обучения:

1. **Открыта** (`none`/`returned`): пустой квадрат → клик = заявка.
2. **На проверке** (`pending`): **одна жёлтая галочка** в контурном квадрате, чип «На проверке ✓», подпись «Ментор проверит и подтвердит — обычно в течение 1–2 дней» (управление ожиданием). Клик — снять заявку (низкие ставки, без confirm-диалога).
3. **Подтверждено** (`approved`): **двойная галочка** на жёлтой заливке, чип «Подтверждено ментором ✓✓». Не кнопка: `title="Изменить может только ментор"` — залоченность и есть видимое лицо контроля ментора. Анимация «одна галочка → двойная» при live-подтверждении = второй момент награды.
4. **Возвращена** (`returned`): чип «Возвращена», **комментарий ментора калаутом прямо на карточке** — фидбек первого класса, не похоронен в колокольчике. Чекбокс снова активен.

**Вкладки «Задач»** получают третью группу: Открытые · **На проверке** · Выполненные — заявленные задачи покидают «открытые» (дыра дизайна B, чиним).

**Мгновенный прогресс, одна истина на странице**: оптимистичные мутации (`onMutate` патчит кэши `['portal','tasks']` и `['portal','roadmap']`; `onError` — откат + toast). Правило заполнения «`done` или `pending` = заполнено» применяется **и к дорожке, и к проценту hero-карточки** (иначе одна страница показывает две правды). Сводка: «Выполнено 4 · На проверке 2». Терминальная галочка узла этапа — только когда все задачи `done` (этап «празднуется» только подтверждённым). Сабтаски-спаны становятся кнопками (правило «ни одного мёртвого афорданса» — на всех трёх поверхностях: Задачи, Главная, Мой roadmap).

**Празднования** — ярусно по редкости, только CSS/keyframes, всё под `prefers-reduced-motion`, ноль новых зависимостей:
- заявка: прорисовка галочки + короткий glow чекбокса (микронаграда мгновенно);
- подтверждение (live через WS): анимация ✓→✓✓ + toast «Ментор подтвердил: «{title}»»;
- этап подтверждён целиком: пульс узла дорожки + скромный particle-burst;
- streaks/milestones — **фаза 3** отдельным дизайном (в текущем виде метрика геймится тогглами).

## 7. UX ментора (workspace)

**Новая страница `/workspace/review` «Проверка задач»** — клон анатомии StatusInboxPage (вкладки → фильтры → карточки с действиями → разобранный хвост), но отдельной страницей: StatusInboxPage смонтирован **дважды** (в workspace и в CRM `/status-inbox` — территория второго разработчика), лезть в него нельзя.
- Карточка: студент (ссылка на `#roadmap`), задача + этап, «отмечена 2 ч назад», чипы приоритета/дедлайна; **Подтвердить** / **Вернуть** (диалог с обязательным комментарием — 422 недостижим из happy path) / **Открыть**.
- Live: `useWsEvent('task.review_requested')` + инвалидация; элементы pending >24ч — акцентная рамка (очередь сама подгоняет SLA).
- Inbox-zero полировка: пустое состояние «Всё проверено ✓», счётчик «Проверено сегодня: N», бейдж с числом pending на пункте навигации.
- Ambient: StatCard «На проверке» на дашборде; на детали студента pending-строки получают чип «ждёт проверки» + инлайн Подтвердить/Вернуть.
- Возвраты — только поштучно (фидбек не бывает оптовым); bulk-подтверждение — стретч.

## 8. Миграция `043_roadmap_task_review`

Enum `task_review_status`; колонки на `roadmap_tasks`: `review_status` (NOT NULL, default `'none'`), `completed_by`/`reviewed_by` (FK users, SET NULL), `completed_at`/`reviewed_at`, `review_comment` — аддитивно, без бэкфилла (существующие done остаются `none` = «внёс ментор», семантически верно). Частичный индекс `WHERE review_status='pending'` под очередь. Даунгрейд обратим.

## 9. Крайние случаи

1. Нет ментора → заявка ок; агрегированная дневная строка mzk/admin; очередь видна им (unscoped staff).
2. Roadmap в архиве → 409; в портале архивный roadmap полностью read-only (чекбоксы отсутствуют, а не «выключены»).
3. Гонка подтверждения и снятия → row lock, проигравший получает 409 + нейтральный toast «Задача уже разобрана».
4. Снять подтверждённое студентом → невозможно (T2 guard).
5. Задача удалена при pending → очередь live-производная, элемент исчезает; протухшая ссылка из колокольчика ведёт на очередь с текущей правдой.
6. Повторная заявка после возврата → сразу можно; прежний комментарий виден до следующего ревью; полная история в `status_history`.
7. Шторм тогглов → идемпотентность, дедуп непрочитанных, коалесинг телеграма, дайджест.
8. Студент без портального аккаунта → ревью работает, студенческие нотификации скипаются.
9. Обрыв WS → все обработчики только инвалидируют ключи; 30s staleTime + поллинг колокольчика: задержка возможна, потеря — нет.

## 10. Тесты (минимум, PR-1)

Матрица прав (~12 кейсов): чужой студент → 404 (без раскрытия существования), coordinator-задача → 403, архив → 409, `ALREADY_DONE`, идемпотентный повтор, T2 не из pending → 409, ревью не из pending → 409, гонка approve/unclaim (две транзакции), T5-развилки (done/не-done), S1 whitelist, эскалация полей заявкой → структурно невозможна, `X-Error-Code` на каждом отказе.

## 13. Критерии приёмки

1. Студент отмечает задачу → дорожка/процент двигаются в кадре клика; ментор видит заявку в колокольчике (live) и в `/workspace/review`.
2. Подтверждение ментора долетает студенту live: ✓→✓✓ + toast; возврат — комментарий на карточке.
3. `status='done'` нигде не появляется без действия staff; все существующие дашборды честны без единой правки.
4. Ни одного мёртвого чекбокса и ни одного тихого 403 во всех трёх порталах-поверхностях.
5. Гонки дают 409 + нейтральный UX, не гибридные состояния.
6. `docker compose exec backend pytest` зелёный, миграция обратима, тест-матрица прав проходит.
