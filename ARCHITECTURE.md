# Архитектура TeenTechEd CRM

Этот документ — про то, **как всё устроено внутри**, а не как запустить проект (для этого см. [README.md](README.md)).

## 1. Общая картина

```
                        ┌─────────────┐
 браузер/Telegram ─────►│   Caddy     │  (в проде — общий, вне этого репо)
                        └──────┬──────┘
                               │
                 ┌─────────────┼──────────────┐
                 │                             │
          ┌──────▼──────┐              ┌───────▼────────┐
          │  frontend   │              │  backend        │  uvicorn (веб-тир)
          │  (Vite/nginx)│             │  FastAPI, async  │  ТОЛЬКО быстрый I/O
          └─────────────┘              └───────┬──────────┘
                                                │ кладёт job
                                         ┌──────▼──────┐
                                         │    Redis    │  очередь (arq) + WS pub/sub + rate-limit
                                         └──────┬──────┘
                                                │ забирает job
                                         ┌──────▼──────────┐
                                         │  worker (arq)    │  единственный процесс —
                                         │  Deepgram/LLM/   │  здесь же живут все
                                         │  Telegram/синки  │  фоновые циклы (см. §4)
                                         └───────┬──────────┘
                                                 │
                              ┌──────────────────┼──────────────────┐
                              │                  │                  │
                       ┌──────▼──────┐   ┌───────▼──────┐   ┌───────▼──────┐
                       │  Postgres   │   │    MinIO     │   │  Внешние API │
                       │             │   │  (S3-совм.)  │   │ Notion/TG/   │
                       │             │   │              │   │ Deepgram/LLM │
                       └─────────────┘   └──────────────┘   └──────────────┘
```

Ключевой принцип: **веб-тир никогда не ждёт внешний API**. Он либо отвечает мгновенно из БД, либо кладёт задачу в Redis-очередь и сразу возвращает управление. Вся медленная, блокирующая работа (внешние HTTP-вызовы, транскрипция, LLM) живёт в отдельном процессе `worker`, который можно перезапускать/масштабировать независимо от сайта.

Это не случайная деталь реализации — это прямое следствие разбора инцидента: раньше транскрипция и Telegram-обработка шли синхронно внутри HTTP-запроса на одном процессе `uvicorn` с маленьким пулом соединений к БД. Если несколько пользователей одновременно запускали тяжёлую операцию — блокировался event loop и пул, и переставал отвечать **весь сайт**, а не только тяжёлая операция.

## 2. Технологический стек

| Слой | Технология | Зачем именно она |
|---|---|---|
| Backend | FastAPI (async), SQLAlchemy 2.0 (async), asyncpg | Async нативно ложится на I/O-bound нагрузку (внешние API, БД) без доп. процессов на запрос |
| Очередь задач | `arq` на Redis | Асинхронный (не нужно переписывать код на sync, как для Celery), не требует отдельного брокера — Redis уже был в проекте |
| БД | PostgreSQL 15 | — |
| Object storage | MinIO (S3-совместимый) | Аудиозаписи сессий, документы, Telegram-вложения |
| Frontend | React 18 + TypeScript, Vite, TanStack Query, Tailwind, Radix UI | — |
| Auth | JWT (access, короткоживущий) + refresh-token в httpOnly-cookie с ротацией | См. §6 |
| Real-time | Нативный WebSocket-эндпоинт + Redis pub/sub для фан-аута между процессами | См. §5 |
| Интеграции | Telegram (aiogram, webhook), Notion API, Google Sheets, Deepgram (STT), OpenAI/Anthropic (LLM-инсайты) | См. §4 |
| Миграции | Alembic | — |

## 3. Web-тир: что здесь можно и нельзя делать

`backend/app/main.py` — только:
- HTTP-роуты (`app/api/v1/endpoints/*`) — быстрые операции с БД.
- WebSocket-эндпоинт (`/api/v1/ws`, в `chat.py`) — держит соединения, локальные для этого процесса.
- Постановка задач в очередь (`app/services/queue.py::get_arq_pool`) там, где нужна медленная внешняя операция.

**Что здесь запрещено с тех пор, как включили несколько uvicorn-воркеров:** запускать в `lifespan` любой цикл-в-фоне через `asyncio.create_task`. Причина: с `--workers N` каждый воркер — отдельный процесс с собственным `lifespan`. Всё, что там запущено, размножается N раз. Раньше так жили Notion-синк, Sheets-синк, payment notifier и Telegram webhook health-check — при переходе на несколько воркеров это дало бы N параллельных синков с Notion и N одинаковых уведомлений админам об одном и том же просроченном платеже. Поэтому все такие циклы перенесены в `worker.py` (см. §4) — единственный процесс, который гарантированно один.

Единственное, что легитимно живёт в per-process `lifespan` — это `ws_hub.manager.start()/stop()` (см. §5): у каждого веб-воркера обязана быть своя локальная таблица сокетов и свой подписчик на Redis-канал.

## 4. Worker-тир (`backend/app/worker.py`)

Отдельный процесс, запускается командой `arq app.worker.WorkerSettings`. Делает две принципиально разные вещи:

### 4.1. Фоновые задачи из очереди (`WorkerSettings.functions`)

| Задача | Что делает | Кто её кладёт в очередь |
|---|---|---|
| `reconcile_audio_task` | Транскрибирует через Deepgram REST все ещё не расшифрованные резервные аудио-чанки сессии, склеивает в `backup_transcript_text` | эндпоинт `POST /note-sessions/{id}/reconcile-audio` (сразу отвечает `queued: true`, фронт поллит статус чанков) |
| `process_telegram_attachment_task` | Скачивает файл из Telegram, транскрибирует голосовые/видео-заметки, грузит в MinIO, при необходимости создаёт `Document` | Telegram-вебхук (`telegram_bot.py::on_message`) сразу после создания строки сообщения |
| `extract_telegram_insight_task` | Прогоняет текст сообщения через LLM (OpenAI/Anthropic с фолбэком) и создаёт `PendingInsight` | либо вебхук напрямую (текстовые сообщения), либо `process_telegram_attachment_task` после того, как расшифровка голосового готова — **специально цепочкой**, чтобы инсайт извлекался из реального текста, а не из пустой строки |

Параметры воркера: `max_jobs=15` (ограничитель — не CPU, а лимиты внешних API), `job_timeout=300`.

### 4.2. Синглтон-циклы (`on_startup`/`on_shutdown` хуки `WorkerSettings`)

Запускаются один раз при старте процесса воркера (не зависят от количества uvicorn-воркеров):
- Регистрация Telegram-вебхука + периодический health-check (`webhook_health_loop`).
- Notion-синк (`notion_sync.sync_loop`, интервал `NOTION_SYNC_INTERVAL_SECONDS`, по умолчанию 3600 сек).
- Google Sheets-синк (`sheets_sync.sync_loop`, интервал `SHEETS_SYNC_INTERVAL_SECONDS`).
- Payment notifier (`payment_notifier_loop`) — уведомления о приближающихся/просроченных платежах.

**Важно:** этот процесс не поддерживает `--reload`. Если правишь код синков/задач — `docker compose restart worker` вручную.

## 5. Redis: три роли на одном инстансе

Один и тот же Redis используется для трёх разных целей — они не конфликтуют, но стоит понимать разделение:

1. **Rate-limiting** (`app/services/rate_limit.py`) — fixed-window счётчики на попытки логина и т.п. Fail-open: если Redis недоступен, лимит не применяется (доступность важнее строгости). IP клиента берётся из `X-Forwarded-For` только при `TRUST_PROXY_HEADERS=true` (бэкенд за Caddy и не опубликован в хост напрямую); иначе заголовок игнорируется, чтобы его нельзя было подделать и обойти throttle по IP.
2. **Очередь `arq`** (`app/services/queue.py`, `app/worker.py`) — задачи из §4.1.
3. **WebSocket pub/sub** (`app/services/ws_hub.py`) — см. ниже.

### WS-хаб и почему это не тривиальный in-memory словарь

Каждый uvicorn-процесс хранит только те WebSocket-соединения, которые физически подключились именно к нему. Если процессов несколько (`--workers N`), сообщение, отправленное пользователю через `manager.send_to_users(...)`, должно дойти до его сокета независимо от того, к какому процессу тот подключён. Поэтому `send_to_users` не рассылает напрямую, а публикует событие в Redis-канал `ws:fanout`; каждый процесс подписан на этот канал и доставляет только тем сокетам, которые держит сам. Fallback на локальную доставку, если Redis временно недоступен.

Это проверено вживую: 6 параллельных WS-подключений одного пользователя, размазанные по 2 независимым uvicorn-процессам, все получили сообщение, отправленное из третьего процесса.

## 6. Аутентификация

- **Access-токен** — JWT, содержит `sub` (user id) и `role`, живёт `ACCESS_TOKEN_EXPIRE_MINUTES` (по умолчанию 60 мин), передаётся в `Authorization: Bearer`.
- **Refresh-токен** — непрозрачная строка, хранится хэшированной в таблице `refresh_tokens`, лежит в httpOnly-cookie (`path=/api/v1/auth`), живёт `REFRESH_TOKEN_EXPIRE_DAYS` (30 дней). Ротируется при каждом `/auth/refresh` — старый помечается `revoked`, выдаётся новый.
- **Grace-период на повторное использование** (`REFRESH_REUSE_GRACE_SECONDS = 20`): если два запроса на рефреш прилетели почти одновременно (типичный кейс — две открытые вкладки), «проигравший» запрос получает не отказ, а токен-преемник по цепочке `replaced_by_hash`. Без этого второй запрос словил бы 401 и разлогинил пользователя, хотя сессия валидна — именно так изначально проявлялся баг "не пускает после логина".
- Пароли — bcrypt.
- **Fail-fast на дефолтных секретах**: в проде (`ENVIRONMENT=production`) `main.py` отказывается стартовать, если `JWT_SECRET_KEY`/`PGCRYPTO_KEY` остались дефолтными (`change-me`) — с дефолтным JWT-секретом кто угодно подделывает токен админа, с дефолтным ключом шифрование ИИН формальное. Упавший прод безопаснее молча дырявого. Менее критичные дефолты (пароль сид-админа, ключ MinIO) — только громкий `critical`-лог.
- **Загрузки файлов** читаются с ограничением (`app/core/uploads.py::read_upload_capped`, чтение чанками с обрывом на лимите), а не `await file.read()` целиком — иначе большим файлом можно посадить процесс по памяти до проверки размера.
- Роли: `admin`, `mzk_manager`, `mentor`, `student`. Права проверяются на уровне эндпоинтов (`_assert_staff`/`_assert_view`-подобные хелперы в каждом роутере), а не на уровне единого middleware — у каждого домена своя модель доступа (например, ментор видит только "своих" студентов через `mentor_scope.require_student_access`).

## 7. Домены данных и ключевые модели

- **Студенты и договоры**: `Student`, `Contract` (со статусом пайплайна `PipelineStatus`), `Payment`.
- **Roadmap**: `RoadmapTemplate` (шаблон, авторский, admin/mzk_manager) → `Roadmap` (живой, привязан к студенту). **У студента может быть несколько одновременно активных `Roadmap`** (например, параллельные заявки в разные страны) — ограничения "один активный на студента" больше нет; студент их только просматривает, редактируют только сотрудники (см. ниже).
- **Заметки сессий**: `NoteSession` (встреча/созвон) → `NoteTranscript` (текст, живой поток) + `NoteSessionAudioChunk` (резервные аудио-куски по 5 минут на случай обрыва live-транскрипции).
- **Telegram**: `TelegramChat` (группа/чат) → `TelegramChatSession` (окно активной сессии с конкретным студентом) → `TelegramMessage` → `TelegramAttachment`.
- **Notion-зеркало**: `NotionSnapshot` — построчная копия Notion-таблицы с матчингом на `Student` (fuzzy-match по имени/телефону + ручная привязка).
- **Уведомления**: `Notification` — персональные, на пользователя; пушатся через WS-хаб и видны в общем колокольчике.

### Права студента на Roadmap

Студент **не может** менять статус этапов/задач/подзадач — эти PATCH-эндпоинты (`/stages/{id}`, `/roadmap-tasks/{id}`, `/roadmap-subtasks/{id}`) требуют роль из `STAFF` (admin/mzk_manager/mentor-в-scope). Студент только просматривает прогресс и заполняет анкеты (отдельный домен `questionnaires`), привязанные к задачам. Это осознанное ограничение, а не недосмотр — раньше студент мог сам отмечать задачи выполненными, что расходилось с процессом (прогресс подтверждает только ментор).

## 8. Внешние интеграции — паттерн для каждой

| Интеграция | Как получаем данные | Куда идёт медленная часть |
|---|---|---|
| **Telegram** | Push-вебхук (`aiogram`, `set_webhook`), не polling | Скачивание файла, транскрипция, LLM — в `worker` (§4.1) |
| **Notion** | Поллинг (у Notion нет нативных webhook на изменение строк базы) — раз в час, крутится в `worker` | Сам HTTP-запрос к Notion уходит в `run_in_executor`, чтобы не блокировать event loop |
| **Google Sheets** | Поллинг через `gspread` + service account | Аналогично, в `worker` |
| **Deepgram** | Два независимых пути: (1) live-транскрипция — прямой WebSocket **с фронтенда** в Deepgram (в обход нашего backend, через короткоживущий токен из `/integrations/deepgram/token`); (2) резервная транскрипция — REST API, только в `worker` | — |
| **OpenAI/Anthropic** | Запрос-ответ с фолбэком (`ai_client.py::complete_with_fallback`) | Только в `worker`, никогда в вебхуке/запросе напрямую |

## 9. Масштабирование (актуально для `docker-compose.prod.yml`)

- **Web-тир**: `uvicorn --workers ${UVICORN_WORKERS}` (по умолчанию 2). Формула — число воркеров ≈ число доступных ядер CPU контейнера (для async это не "2×cores+1", как у sync-фреймворков: один воркер уже держит сотни соединений, воркеры нужны, чтобы задействовать несколько ядер). Перед изменением — проверить реальное число ядер (`nproc` на хосте).
- **DB pool**: `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` для веб-тира и отдельно `WORKER_DB_POOL_SIZE`/`WORKER_DB_MAX_OVERFLOW` для воркера (меньше — задачи держат сессию недолго). Общая формула: `N_web × (DB_POOL_SIZE + DB_MAX_OVERFLOW) + (DB_POOL_SIZE_worker + DB_MAX_OVERFLOW_worker) < Postgres max_connections`.
- **Worker**: 1-2 процесса `arq` достаточно даже под сотню одновременных пользователей — узкое место не CPU, а лимиты внешних API (Deepgram/OpenAI).
- **Прод-устойчивость** (`docker-compose.prod.yml`): у всех сервисов ротация логов (`json-file`, `max-size 10m × 3` — иначе логи забивают диск), лимиты памяти бэкенду/воркеру (одна утечка не должна съесть весь сервер), healthcheck'и (postgres `pg_isready`, redis `ping`, minio `mc ready`, backend `GET /health`), а `backend`/`worker` стартуют только после `condition: service_healthy` у зависимостей.
- Сознательно **не** делаем на этом масштабе: Kubernetes, read-реплики Postgres, несколько контейнеров backend за собственным балансировщиком (вместо `--workers` внутри одного) — это решает проблемы на порядок большего масштаба и добавляет операционную сложность без пользы здесь.

## 10. Три поверхности фронтенда — зачем их три

- **Классический CRM** (`/students`, `/finances`, `/statistics`, ...) — светлая тема, изначальный UI.
- **Workspace** (`/workspace/*`) — тёмная тема, тот же функционал для ментора, переработанный UX (единая карточка студента с вкладками вместо множества страниц).
- **Portal** (`/portal/*`) — кабинет студента, светлая тема токенов `p-*`, доступен только роли `student`.

Общая бизнес-логика — в `components/shared/*` и общих API-клиентах (`api/roadmap.ts` и т.д.), стилизация — через раздельные наборы Tailwind-токенов (`ds-*` дефолт, `p-*` портал, `w-*` workspace), не через дублирование компонентов, где это возможно.

## 11. Эксплуатация: бэкапы, CI/CD, наблюдаемость

### Бэкапы БД
- `scripts/backup.sh` — `pg_dump | gzip` с проверкой целостности дампа, ротацией (`BACKUP_RETENTION_DAYS`, по умолчанию 14 дней) и off-site копией в MinIO. Ставится в cron на проде (`0 3 * * *`). Восстановление — `scripts/restore.sh <дамп>`.
- Деплой делает `backup.sh` **перед** накатом миграций (миграции идут в `command:` бэкенда и без дампа необратимы).

### CI/CD (`.github/workflows/deploy.yml`)
- Пуш в `main` → job `validate` (lint фронта неблокирующий, `vitest`, `pytest`, применение схемы+миграций на чистом postgres — повторяет прод-старт `bootstrap_db` + `alembic upgrade head`, проверка единственного alembic head, валидация compose) → только при успехе job `deploy` по SSH.
- `main` = прод: зелёный CI — единственный барьер перед деплоем к пользователям.

### Наблюдаемость (стек в `monitoring/`)
Четыре независимых слоя:
- **Ошибки** → Sentry: бэкенд (`sentry-sdk`, `main.py::_init_sentry`) и фронтенд (`@sentry/react`, `main.tsx`), включаются при заданном `SENTRY_DSN`/`VITE_SENTRY_DSN`, `send_default_pii=False` (не шлём ПДн студентов).
- **Метрики** → Prometheus + Grafana: хост (node_exporter), контейнеры (cAdvisor), приложение (`/metrics` через `prometheus-fastapi-instrumentator` — RPS, латентность, коды по эндпоинтам; наружу не торчит, Caddy его не проксирует), БД (postgres_exporter), Redis (redis_exporter).
- **Логи** → Loki + Promtail: поиск по логам контейнеров в Grafana вместо `ssh + grep`.
- **Алерты** (`monitoring/prometheus/alerts.yml`): сервис/бэкенд/postgres/redis лёг, CPU/RAM/диск, доля 5xx, близость к лимиту памяти, устаревший бэкап (`backup.sh` пишет `tte_backup_last_success_timestamp_seconds` в textfile-коллектор node_exporter).

Стек слушает только `127.0.0.1` (доступ через SSH-туннель). Подробности запуска — в [monitoring/README.md](monitoring/README.md).

## 12. Если что-то не так

- Прод упал после деплоя с `UndefinedColumnError` — почти всегда забыли `alembic upgrade head`. Это должно быть частью деплой-чеклиста, не полагаться на память.
- Сайт тормозит при нескольких одновременных тяжёлых операциях (запись/транскрипция) — проверь, что `worker` реально поднят и не упал (`docker compose ps`, `docker compose logs worker`) — без него задачи просто копятся в очереди и никогда не выполняются.
- Уведомления/чат приходят через раз при нескольких uvicorn-воркерах — проверь, что Redis доступен обоим (`ws_hub` тихо деградирует до локальной доставки, если Redis недоступен, — это может маскировать проблему).
- Непонятно, что вообще происходит на проде — смотри наблюдаемость (§11): ошибки в Sentry, графики нагрузки и `up`-статусы в Grafana, логи с поиском в Loki. Быстрый локальный взгляд — `docker compose -f docker-compose.prod.yml ps` (колонка health) и `docker stats`.
- Бэкенд не стартует в проде с ошибкой про дефолтные секреты — это ожидаемо (fail-fast, §6): задай реальные `JWT_SECRET_KEY`/`PGCRYPTO_KEY` (32+ случайных символа) в `.env`.
