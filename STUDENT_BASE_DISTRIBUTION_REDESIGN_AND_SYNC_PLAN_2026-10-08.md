# Общая база, Распределение и согласование данных

Дата: 08.10.2026. План для реализации после изучения кода. В этом документе зафиксированы требования к интерфейсу из задачи пользователя и отдельно — новая задача автоматизации. Работающий код и данные этим документом не меняются.

## 1. Два независимых этапа

### Этап A — редизайн интерфейса

Переделать только страницы `/students` («Общая база») и `/students/distribution` («Распределение») по макетам A и D из задачи. Сохранить действующие API, обработчики, права, назначения, статусы и привязки. Страницы «Обзор» (`/dashboard`) и «Мои студенты» не менять. Существующие действия разрешено переносить и группировать, но не удалять. Использовать текущую дизайн-систему и её светлую/тёмную темы. Сверить визуальный результат со скриншотами, а не только с текстом этого плана.

### Этап B — автоматизация источников

После отдельной проверки этапа A изменить серверную обработку Notion и Google Sheets: безопасно привязывать источники к существующим студентам, создавать карточку спустя 24 часа только при отсутствии кандидатов и согласовывать общие редактируемые поля CRM ↔ Notion. **Это отдельное изменение моделей, API/фоновых задач и миграций**; запрет на изменение данных и контрактов относится к этапу A и не должен маскировать требуемую серверную работу этапа B. Миграция добавляет служебные метаданные, не переписывает существующие статусы и назначения. Не включать автоматическую запись на проде вместе с первым выпуском нового интерфейса.

## 2. Проверенные факты проекта

- «Общая база» начинается с неархивных `Student`: одна строка — один студент CRM. Статус CRM берётся из последнего договора. Страны — из заявок CRM. Активные сотрудники — из `MentorAssignment`. Поля Notion показываются только по связанной записи `NotionSnapshot`.
- «Обзор» начинается со страниц Notion из локальных `NotionSnapshot`, включая страницы без студента CRM. Снимок содержит исходные и нормализованные значения, время изменения страницы и состояние связи. Синк Notion сейчас обновляет зеркало, но не переносит поля в CRM автоматически.
- Кнопка «Синхронизировать» в Общей базе запускает импорт анкет **Google Sheets**, а «Синк Notion» обновляет зеркало Notion. Подпись «Синхронизировать всё (платформа ↔ Notion)» использовать нельзя.
- Две формы Google Sheets — «Пакет сопровождения» и «Кейсы студентов» — попадают в `IntakeSubmission`. При текущем `ENABLE_INTAKE_AUTO_CREATE=true` анкета без кандидата может стать студентом сразу, без ожидания суток. Связанный студент дозаполняется только по пустым безопасным полям; финансовые суммы и личные договорённости не переносятся автоматически.
- Автопривязка Notion сейчас допускается при уверенности `1.0`; анкеты Sheets с кандидатом остаются для ручной обработки. `fuzzy_match` возвращает одного кандидата и при одинаковом телефоне может выбрать первого, поэтому одного его результата недостаточно для безопасной массовой привязки разных источников.
- Роли для ручного назначения: `career` (Профориентолог), `ielts` (Учитель IELTS), `lead` (Ментор по УП), `country` (Ментор по стране), `portfolio` (Портфолио), `mzk` (МЗК). `country` допускает нескольких сотрудников по разным странам. Обязательные роли для существующего `team_readiness` — только `career`, `ielts`, `lead`, `country`; МЗК и Портфолио в него не входят. Термин **«Неполная команда» не использовать**.
- Реальные статусы CRM: «Работа окончена — Поступил», «Работа окончена — Передумал», «Пропал абитуриент», «Не оплачено», «На возврате», «Пауза», «Активная работа», «На визе», «Проблема», «Подвешено», «Пересдача IELTS», «Переподача», «Перевели на другой продукт», «Нет статуса». Notion хранит свои текстовые варианты; для сравнения использовать существующий `parse_pipeline_status`. **«В работе» по умолчанию = только `active_work`**, остальные статусы выбираются фильтром. Цвет бейджа не определяет бизнес-статус.
- Текущая массовая ручка назначения ограничена 200 студентами за запрос. Результат может быть частичным: `assigned`, `replaced`, `already`, `skipped`; замена требует причины. Новая оболочка обязана сохранить этот сценарий и сообщение об ожидании подписи регламента.

## 3. Этап A: Общая база

### 3.1 Шапка и навигация

Eyebrow «СТУДЕНТЫ», заголовок «Общая база». Мета-строка показывает фактическое количество **CRM-студентов в выборке**, дату/время последнего успешного синка Notion и число непривязанных страниц Notion. Числа не хардкодить. Ссылка на непривязанные страницы открывает действующую панель привязок; отдельную предупреждающую строку убрать.

Справа: «Распределение», меню «Данные», «Экспорт», «+ Студент». В меню «Данные» с прежними обработчиками: «Синхронизировать анкеты Google Sheets», «Обновить данные Notion», «Входящие анкеты · N», «Обзор Notion» (переход на существующий `/dashboard`), «Привязки Notion · N». Различать переход в Обзор и очередь привязок. Показывать пункты согласно текущим правам. В этом меню не обещать двусторонний синк до этапа B.

### 3.2 Вкладки

«Все N» · «Требуют назначения N» · «Расхождения с Notion N» · «Мои N». «Требуют назначения» — студент `active_work` по связанной странице Notion, у которого нет хотя бы одной из **четырёх обязательных ролей**, либо отдельный уточнённый пользователем набор условий. Слов «Неполная команда» и «готовность 4/6» не использовать. «Мои» — есть активное назначение текущего пользователя в любой роли. «Расхождения» — только связанные студенты и только реально сопоставимые поля; неизвестное значение = «не сверено», не расхождение.

Один порядок подсчёта для всех вкладок: исходный набор неархивных CRM-студентов → общий поиск и общие фильтры → условие выбранной вкладки. Счётчик каждой вкладки вычислять из набора после общих фильтров, **без условия текущей вкладки**. Один студент считается один раз.

### 3.3 Поиск, фильтры, группировка, поля

Поиск: имя, телефон; город добавить только если он реально реализован в фильтрации и не нарушает правило «только оболочка» этапа A. Переиспользовать визуальные компоненты фильтров Обзора (`PipelineToolbar`, `viewState`), но сохранить семантику CRM-списка.

Быстрые фильтры: Набор/Intake, Lead-Mentor, Degree, Страна, Ответственный. «+ Фильтр» должен содержать **все существующие фильтры Общей базы**: Все/Мои/С ответственными/Без ответственного; множественный статус CRM («совпадает»/«не совпадает»); год, ступень, страна («любая»/«основная»), программа/услуга, сотрудник и роль, связанное поле Notion, а также «Контроль работы»: нет roadmap, нет ближайшей встречи, Telegram не привязан, незакрытые/просроченные задачи, открытые обращения, документы на проверке, перепродление, ментор только по имени. Сохранить URL-фильтры при переходе с Распределения и чипы для снятия каждого условия. Не заменять CRM-фильтры набором полей Notion.

В подписях и логике различать `students.intake_year` и `Intake` Notion, статус договора и `Статус выплат` Notion, реальное назначение `lead` и текст `Lead-Mentor` Notion, основную страну заявок CRM и `Main country` Notion. Фильтр по Notion работает только для **связанных** страниц. При ошибке Notion CRM-список остаётся доступным.

Группировка: Набор · Ответственный (с выбором роли, по умолчанию МЗК) · Статус. Пустая группа явно подписана «Без ...». Сортировка по имени и настройка видимых столбцов не должны прятать доступ к существующим действиям. Сохранять вид/группу/поля локально либо в URL; переход по ссылке с заданными фильтрами имеет приоритет над сохранённым состоянием.

### 3.4 Таблица, карточка, назначения

Две строки заголовков по макету A: Студент / Процесс / Команда / Документы. Одна строка — CRM-студент. Отдельные статусы CRM и Notion не склеивать. В ячейке расхождения показывать нормализованное сравнение и источник. «Ментор только по имени» из импорта не выглядит как активное назначение.

Шесть ролей можно показывать компактными ячейками; число «4/6» подписывать **«Назначено 4 из 6 ролей»**. Для `country` показывать несколько назначений или число с раскрытием, сохраняя страну каждого. Не терять состояние `awaiting_signature` и плейсхолдер `required`. Клик по пустой роли вызывает существующий механизм назначения; замена сотрудника требует прежнего диалога причины. Если действие «Снять назначение» существует и разрешено текущему пользователю, показывать его; иначе не рисовать активную кнопку.

Выбор строк, групп и массовое назначение применяются только к видимому набору после всех фильтров. При частичном успехе показывать фактически назначенных, уже назначенных и пропущенных, затем запросить причину только для замен. Выделение не должно незаметно переживать смену роли, вкладки или фильтра так, чтобы операция задела скрытые строки.

Правая карточка до 620px: краткий профиль, ссылка на связанную страницу Notion и полную карточку CRM, сравнение существующих общих полей, шесть ролей с фактическими назначениями, существующая история назначений, признаки обеих анкет Google Sheets. Если связи с Notion нет, показывать «Не связано», а не «Всё совпадает». Действия «Взять из Notion» / «Оставить в CRM» показывать только там, где уже есть поддерживаемое действие с нужными правами; не изобретать новый endpoint в этапе A.

### 3.5 Выгрузка

Сохранить существующий диалог: набор данных (`all`, `notion_active`, `platform_access`, `status_mismatch`), дополнительные условия (доступ, активный чат, МЗК, ментор), выбор полей, XLSX/CSV. В текущем коде он **не наследует фильтры видимой таблицы**. Ясно подписать это в UI. Экспорт текущей выборки считать отдельным расширением, если его нельзя обеспечить существующим API без изменения контракта.

## 4. Этап A: Распределение

Шапка по макету D: «← К общей базе», eyebrow «СТУДЕНТЫ В РАБОТЕ», заголовок, точные числа CRM-студентов со статусом `active_work` по связанной странице Notion и непривязанных страниц Notion. Ссылку на очередь привязок оставить; большой блок сверки свернуть до неё.

Шесть вкладок реальных назначаемых ролей без чисел; справа существующий переключатель «Список студентов / Доска нагрузки». **Доску с перетаскиванием не менять.** При смене роли сбрасывать выбранные строки, сотрудника и раскрытие групп.

В списке: поиск; фильтр сотрудника текущей роли; «Только без <роль>» по умолчанию; Набор, Lead-Mentor, Degree, Страна и дополнительные реально доступные поля. Для Notion-фильтра без связанной страницы не подставлять CRM-значение молча. Группировка: Набор (по умолчанию), Lead-Mentor или Страна; у каждой подписи указать источник. Сводка и правая панель «Кто ведёт» считают тех же студентов, что таблица, после общих фильтров. Различать число уникальных студентов и число назначений: `country` — мульти-роль.

Таблица-матрица: группы свёрнуты, кроме первой; поиск/выбранный сотрудник раскрывает нужные группы; рендерить по 15 строк с «Показать ещё 15». Групповой чекбокс выбирает только доступные для действия строки в текущей группе. Шесть колонок ролей; выбранная роль визуально выделена. «+» в пустой ячейке переводит к выбору сотрудника через прежний механизм. Для уже назначенной роли показывать имена; `country` может содержать нескольких сотрудников и их страны. Правая панель перечисляет «Без ответственного» и сотрудников с точными числами; никакой выдуманной нормы нагрузки, шкал или процентов.

После назначения обновить Общую базу, Распределение и счётчики через существующую инвалидацию запросов. Сохранить частичный результат, причину замены, право на назначение и состояние ожидания подписи. При 400+ строках свёрнутые группы не рендерить; горизонтальная прокрутка только внутри таблицы.

## 5. Этап B: проблема №1 — анкеты и страницы создают дубли

### Почему сейчас риск есть

Google Sheets создаёт карточки для анкет без кандидата **сразу** при включённом `ENABLE_INTAKE_AUTO_CREATE`. Notion сам привязывает только точные совпадения, а массовое создание из Notion — отдельная ручная операция. Источники сопоставляются в основном с CRM, а не друг с другом. Совпадение одного телефона или первого подходящего имени может быть неоднозначным; записи двух форм одного студента и страница Notion могут прийти в разное время. Отдельные проходы worker и API могут выполняться одновременно. Задержка в 24 часа снижает риск, но сама по себе не доказывает, что совпадений нет.

### Целевое правило

Для каждой новой записи Notion и Google Sheets сначала искать **уже связанную CRM-карточку**, затем кандидатов среди всех неархивных CRM-студентов, затем среди ещё не обработанных записей **обоих** внешних источников. Одна карточка CRM может иметь страницу Notion и обе анкеты Sheets; одна страница Notion — только одного студента. Привязка по сохранённому внешнему ID имеет приоритет над поиском по имени.

Автоматически привязывать **только одного однозначного кандидата**, подтверждённого достаточными независимыми признаками. Точный телефон в одиночку не гарантирует уникальность; учитывать ФИО/транслитерацию, год, город и уже существующие связи. При нескольких кандидатах, конфликте идентификаторов, ручной отвязке, скрытии записи, архивной карточке или сомнительном совпадении — очередь «Проверить», без создания и без автопривязки. Показывать причины и кандидатов человеку.

Если **через 24 часа от первого появления записи в локальном staging** всё ещё нет ни CRM-карточки, ни однозначного/сомнительного кандидата в Notion или Sheets, и после ожидания прошли успешные полные чтения **обоих настроенных источников**, создать **ровно одну** карточку. Повторить поиск прямо перед созданием. Если внешняя система недоступна или синк неполный, срок ожидания не превращается в разрешение на создание — оставить запись в ожидании. Запись с пустым/невалидным именем не создавать автоматически. Исходные строки Notion и обеих форм после создания привязать к одной карточке. Безопасные поля профиля можно заполнить по существующим правилам; суммы, договорённости, назначения и доступ в кабинет автоматически не создавать.

Сделать операцию идемпотентной между worker/API-процессами: блокировка строк или ключа личности на уровне БД, уникальность внешних ID, повторная проверка перед коммитом, журнал результата и возможность безопасного повтора. Перевести нынешний немедленный `promote_new_submissions` на правило 24 часов; ручные кнопки оставить, но показывать предупреждение о кандидатах. Существующие связи не пересопоставлять массово без отдельной проверки.

### Сценарии приёмки

1. Студент уже есть в CRM → новая анкета/страница однозначно привязана, второй студент не создан.
2. Сначала анкета «Пакет», позже «Кейсы» и Notion → все три записи связаны с одной карточкой.
3. Сначала Notion, позже анкета → то же.
4. Похожее имя, общий телефон, два кандидата или транслитерация → очередь проверки, без автоматического создания.
5. Совпадений нет, оба синка успешны, прошло менее 24 часов → ожидание; прошло 24 часа → одна карточка и связи.
6. Источник недоступен, запись скрыта/отвязана вручную, два прохода стартовали одновременно → без нежелательной карточки и повторной привязки.

### Отдельный риск: правка уже полученной анкеты Google Sheets

Текущий `row_fingerprint` основан на источнике, времени ответа и ФИО. Синк пропускает знакомый fingerprint: изменение других ячеек строки не обновит `raw_data`, а исправление ФИО может выглядеть новой анкетой. Для этапа B нужен устойчивый идентификатор ответа/строки источника и ревизия содержимого; если Google Forms/Sheets не даёт устойчивого ID, сначала определить безопасный составной ключ и поведение при вставке/перестановке строк. Обновление существующего ответа должно создать новую версию staging-записи, а не нового студента. При изменении имени или телефона заново оценить связь; сомнительную новую личность отправить на проверку, не переносить анкету автоматически на другого человека.

Существующие ранее созданные карточки обрабатывать отдельным сухим прогоном на дубли. Запуск нового правила не должен сам объединять их или менять текущие связи. Для старых анкет возраст отсчитывать от первого зафиксированного появления в staging, а не от времени первой обработки новым кодом; однако старый backlog нельзя автоматически создать без инвентаризации и проверки успешности обоих источников.

## 6. Этап B: проблема №2 — изменения CRM и Notion расходятся

### Почему «последняя перезапись побеждает» пока нельзя включить напрямую

Сейчас Notion хранит время **последнего изменения страницы**, а не каждого свойства. `Student.updated_at` не является временем изменения всех полей договора, заявок и назначений. В `synced_baseline` есть последнее согласованное значение некоторых полей, но нет надёжного события для каждого изменения каждой стороны. Два редактора могут изменить одно поле между опросами; запись синхронизации сама обновит время страницы и может запустить обратное эхо. Поэтому сравнение двух общих timestamp или слепое «последний poll победил» способно затереть более свежую человеческую правку.

### Целевое правило по полям

Создать **реестр сопоставляемых полей**: ключ CRM, свойство Notion, тип, нормализатор, допустимые значения, возможность записи в обе стороны, политика пустого значения и политика конфликта. Начать с общих редактируемых полей, уже присутствующих в сравнении: ФИО, телефон, ступень, год набора, статус, дата договора и поддерживаемые финансовые поля. Для каждого поля сохранять последнее согласованное значение/ревизию и происхождение изменения. CRM-изменения фиксировать в момент успешной транзакции поля; Notion-изменения определять сравнением нового снимка с предыдущим, с временем страницы как **приблизительной отметкой**, а не точным временем поля.

Если изменена только одна сторона после согласованной версии — переносить её значение на другую сторону, перечитать и подтвердить запись, затем обновить baseline. Если обе стороны изменились, автоматический выбор разрешён **только когда порядок именно этих двух изменений достоверен**. Более позднее человеческое изменение тогда побеждает. Если порядок нельзя установить по доступным событиям, сохранить оба значения и отправить поле в очередь конфликта; ничего не затирать. Пустое значение не считать командой удалить без явного пользовательского изменения. Повторы записи не должны создавать цикл CRM → Notion → CRM.

Назначения сотрудников, роли, аккаунты, Telegram-чаты, анкеты, произвольный текст Notion, формулы/rollup и финансовые поля без однозначной карты **не участвуют** в автоматическом last-write-wins. Реальное назначение продолжает меняться только существующим механизмом CRM; текст `Lead-Mentor`/`Mentors`/`МЗК` Notion показывать для сверки. Если бизнесу нужна одинаковая видимость этих имён, отдельно проектировать безопасное одностороннее отображение/запись, не превращая текст Notion в назначение.

Google Sheets — источник **ответов анкет**, а не третья копия всех полей CRM. Изменения ответа формы сохранять как новую версию источника и сравнивать с CRM; автоматическое переписывание ответов Google Sheets не включать без явного решения владельца процесса.

### Надёжность и видимость

Использовать очередь исходящих записей с повтором, idempotency key, проверкой версии перед записью в Notion, проверкой результата после записи, аудитом «кто/что/откуда/когда» и отдельным статусом ошибок. Показывать на карточке и в Общей базе: «Совпадает», «Ожидает синка», «Конфликт», «Ошибка синка», время последнего успешного обновления. Если источники недоступны, отображать последнюю известную версию с временем, не обещая актуальность «везде».

Автоматизацию включать постепенно: инвентаризация полей → сухой прогон и отчёт потенциальных перезаписей → пилот на тестовых/выбранных карточках → наблюдение за конфликтами и дублями → расширение. До первого автоматического переноса сохранить резервную копию и возможность отключить фоновые записи без остановки просмотра.

### Сценарии приёмки

1. Пользователь меняет поддерживаемое поле CRM → после обработки то же нормализованное значение в Notion; повторный синк ничего не меняет обратно.
2. Пользователь меняет поддерживаемое поле Notion → значение приходит в CRM, сохраняется в аудите и видно в обоих интерфейсах.
3. Правки на обеих сторонах с доказуемым порядком → побеждает последняя; без доказуемого порядка → конфликт без потери обоих значений.
4. Notion временно недоступен/отклонил запись → задача повторяется, CRM-правка не теряется, интерфейс показывает ожидание/ошибку.
5. Ручная привязка/отвязка, смена статуса, назначение и финансовые формулы не перезаписываются из чужого поля или из устаревшего снимка.

## 9. Проверка реализуемости без изменения API на этапе A

Перед кодом агент обязан составить таблицу «требование макета → существующий endpoint/поле → доступно данной роли → реализуемо без нового API». Например, матрица шести ролей может строиться из уже возвращаемых `responsibles`, но данные `Lead-Mentor` Notion не входят в ответ доски распределения и потребуют безопасного сопоставления с существующим запросом Notion; не каждый пользователь доски имеет право читать этот запрос. Если поле или счётчик нельзя корректно получить с существующими правами и полным набором строк, не имитировать его и не подставлять данные другого источника. Отметить точный пробел в отчёте и вынести серверное расширение за пределы этапа A.

Общая база сейчас запрашивает до 2000 студентов, затем применяет часть фильтров в браузере. Счётчики вкладок и групп нельзя подписывать как итоги всей базы, если ответ усечён. Сохранить явное значение `total` API, сообщить об ограничении и не экспортировать «текущие фильтры» как эквивалент всех строк без отдельной серверной поддержки.

### Проверенные ограничения перед началом работы

- `GET /mentor-assignments/board` отдаёт одну роль за запрос, один основной регион/страну, не отдаёт `country_scope` и текст `Lead-Mentor` Notion. Полную матрицу шести ролей и фильтр Notion нельзя достоверно собрать только из этого ответа. `GET /students` содержит список `responsibles`, но ограничен 2000 строками. Не показывать неполную матрицу или счётчики как полные.
- Право `assignment_overview:view` не равно `notion:manage`. Сотрудник, видящий распределение, может не иметь права на `GET /notion/pipeline-table`; для него Notion-фильтр скрыть или отложить до отдельного согласованного API/права.
- `country` может повторять одного студента в нескольких колонках доски; суммировать колонки для числа уникальных студентов нельзя. Имена сотрудников в ячейке роли и страна каждого назначения должны подтверждаться доступными данными, иначе показывать только то, что подтверждено.
- Диалог экспорта на Общей базе сейчас показывается без проверки `export:manage`, хотя сервер её требует. В редизайне привести видимость кнопки к существующему праву.
- Для массового назначения использовать существующие кандидаты `users/listAssignable(role)`, `POST /mentor-assignments/bulk` и существующий диалог причины замены. Для страницы распределения сохранить `DistributionBoard.tsx` без изменений.

Ограничения этапа A: текущий API доски распределения отдаёт назначения только выбранной роли и одну основную страну; API не даёт полную матрицу шести ролей или фильтр Lead-Mentor для этой страницы. UI показывает только проверенные различия и помечает непроверенную сводку; серверное расширение планируется отдельно.

### Этап B — синхронизация

Реализована безопасная инфраструктура и ограниченный первый профильный пилот в коде. `ENABLE_INTAKE_AUTO_CREATE`, `ENABLE_INTAKE_AUTO_LINK` и `ENABLE_NOTION_FIELD_SYNC` по умолчанию `false`; дополнительный `NOTION_FIELD_SYNC_DRY_RUN` по умолчанию `true`. Новые автоматические записи и миграции реальной БД в этом сеансе не запускались.

- Google Sheets staging теперь использует ID ответа или Timestamp как ключ, хранит хеш/ревизию и первое/последнее появление; изменения ФИО/телефона и сомнительная идентичность требуют проверки. Устаревшие строки получают `first_seen_at` от `created_at`.
- Матчинг собирает все подходящие CRM-кандидаты. При сильном единственном совпадении по ФИО/транслитерации Sheets можно автопривязать через прежнее заполнение безопасных пустых полей; одного телефона для этого недостаточно. Пара «Пакет» + «Кейсы» соединяется только при взаимно сильном совпадении, без конфликтующего телефона и CRM-кандидатов; после суток создаётся одна карточка и обе анкеты связываются с ней.
- Автоматическое создание одиночной заявки требует суток после последней ревизии, полного успешного чтения обеих форм и успешного Notion-синка новее этой ревизии. Конкурентные запуски ограничивают блокировку основным батчем и найденными парными строками.
- Notion-синк автопривязывает только одного сильного кандидата по имени/транслитерации, запрещает phone-only и ручную отвязку, учитывает уже привязанную страницу. Создание через ручные Notion-действия останавливается при любом правдоподобном CRM-кандидате.
- Добавлена отдельная проверяемая политика поля CRM ↔ Notion: неизвестный baseline, конфликт и неподтверждённая очистка не выбирают победителя; аудит подтвердил, что `Student.updated_at` и `NotionSnapshot.notion_last_edited_at` не дают точного порядка изменения отдельных полей. Реестр baseline пополнен однозначно сопоставленным `mentor_total`.
- Повторная проверка staging нашла и исправила нестабильный ключ: точные дубли больше не превращаются в новую заявку, если экспорт в следующем цикле вернул одну строку; варианты одного Timestamp с разным содержимым получают стабильные ключи и остаются на ручной проверке.
- Добавлена идемпотентная outbox-очередь с lease/`SKIP LOCKED`, попытками и безопасной повторной обработкой. Первый runtime поддерживает только `ФИО`, `телефон`, `Degree`, `Intake`; перед изменением он сверяет живое значение именно этого свойства, текущее CRM-значение и связь страницы с карточкой. Общее изменение постороннего свойства Notion не отменяет задачу; повтор после успешного внешнего PATCH восстанавливает snapshot/baseline без второго PATCH.
- Обработчик подключён к завершению штатного Notion-прохода ограниченной пачкой. При включённом пилотном флаге и `NOTION_FIELD_SYNC_DRY_RUN=true` он только проверяет маппинг/значения и отмечает очередь `dry_run`; запись невозможна. Dry-run-элементы допускаются к записи только после отдельного явного `NOTION_FIELD_SYNC_DRY_RUN=false`. Пилотный флаг сейчас выключен.

Это **не означает**, что правило «последняя правка побеждает» уже выполнено для всех полей: источники пока не дают надёжные события времени изменения каждого поля. Если CRM и Notion оба изменились после baseline, система сохраняет конфликт, не угадывая победителя. Денежные поля, статусы, Lead-Mentor, страны, назначения и очистки не входят в первый runtime-пилот.
