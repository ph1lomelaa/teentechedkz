# Проверка подключения TrustMe

В корневом `.env` задайте:

```dotenv
TRUSTME_LOGIN="номер или логин кабинета"
TRUSTME_PASSWORD="пароль кабинета"
TRUSTME_COMPANY_ID=
```

Сохраните начальный `+` и точное написание логина кабинета. Значения с `#`, пробелами и другими специальными символами оформляйте по правилам dotenv. Настоящий пароль не помещайте в `.env.example` и клиентские `VITE_` переменные. `TRUSTME_COMPANY_ID` можно оставить пустым, если у аккаунта ровно одна компания. При нескольких компаниях клиент потребует выбрать ID явно.

Из каталога `backend` с активированным Python-окружением:

```sh
python -m scripts.check_trustme
python -m scripts.check_trustme --name "Жолдас Нурай"
python -m scripts.check_trustme --download SHORT_URL --output /private/tmp/contract.pdf
```

Первая команда проверяет вход, определение компании и обновление токена. Вторая дополнительно ищет варианты имени и выводит число кандидатов. Третья сохраняет PDF выбранного договора, если путь назначения ещё не занят. Существующий файл не перезаписывается. Реальные `shortUrl` получаются из кандидатов/карточки кабинета, а не из номера договора.

Настройки читаются сервером через `app.core.config.settings`; корневой `.env` подключается независимо от рабочего каталога. После изменения настроек перезапустите работающий backend/worker. В Docker существующий `env_file: .env` передаёт значения; для применения изменённых переменных пересоздайте соответствующие сервисы штатной командой развёртывания.

## Использование в коде

```python
from app.services.trustme import TrustMeClient

async with TrustMeClient.from_settings() as trustme:
    result = await trustme.search("Жолдас Нурай", aliases=("Жолдас Нұрай",))
    # Сотрудник проверяет кандидатов и выбирает договор.
    # pdf = await trustme.pdf(selected_short_url)
```

Клиент не выбирает первый найденный договор и не отбрасывает отозванные записи скрытно. `truncated=True` означает, что выдача ограничена лимитом страниц либо сервер повторил страницу. Совпадение написания имени не является подтверждением личности.

Вход отправляет `multipart/form-data` в `/api/authservice/login`; обновление выполняет `refresh_session()`. При HTTP 401/403 у JSON-запроса клиент с настроенными логином/паролем выполняет один повторный вход и один повтор запроса. Это не распространяется на произвольные бизнес-ошибки в HTTP 200. Ошибки скачивания PDF возвращаются вызывающему коду. Токены и пароль не сохраняются клиентом на диск и не включаются в тексты его ошибок.

## Проверено 2026-11-01

- Настоящий вход без браузера и без `X-Trace-Sig`.
- Определение единственной компании и обновление токена с `Authorization`.
- Поиск: 6 результатов на странице 1, пустая страница 2.

## Карточка студента и Cloudflare

В коде добавлен блок «Договоры TrustMe» в «О студенте → Договор и оплаты». Он доступен и без локального финансового договора. Просмотр сохранённых привязок требует `contracts:view`; поиск по корпоративному кабинету, скачивание и изменение привязок — `contracts:manage`. Поиск поддерживает дополнительные варианты имени, включая ФИО родителя. Сотрудник сначала проверяет PDF и подписантов, затем явно подтверждает соответствие студенту. Для актов привязываются только договоры со статусом «Подписан». Отозванные записи остаются видны в поиске.

Привязки хранятся в `trustme_contract_links`. Подготовлена миграция `127` после `126`. Перед включением интерфейса примените миграцию штатной процедурой развёртывания (`alembic upgrade head`), затем обновите backend/frontend. В рамках разработки миграция проверена генерацией SQL; рабочая база не изменялась. Привязки не изменяют финансовые суммы и статусы карточки. Операции привязки/отвязки сохраняются в истории студента. Один документ нельзя одновременно привязать к разным студентам; при ошибке можно убрать связь и выбрать договор заново.

Cloudflare Challenge определяется по `cf-mitigated: challenge`, а HTML с маркерами challenge распознаётся как запасной сигнал. При такой проверке автоматический повторный вход останавливается. API возвращает код `TRUSTME_CHALLENGE_REQUIRED`, интерфейс показывает ссылку на кабинет и возможность загрузить договор вручную в существующий раздел «Документы». [Официальное описание сигнала Cloudflare](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/).

Подтверждение в браузере пользователя не переносится на сервер автоматически. Если сервер остаётся заблокирован, вопрос доступа нужно решать с администратором/TrustMe. Обход или автоматическое решение challenge не реализованы.

Генерация актов — следующий отдельный этап. Срок жизни токена и поведение при других способах входа не установлены; внутренние адреса кабинета могут меняться.

Проверки этапа карточки: 24 теста backend, 13 тестов интерфейса/навигации и 9 проверок подключения прав прошли. SQL миграции `126:127` сформирован Alembic без подключения к рабочей базе. Интерфейс осмотрен в браузере на вымышленных данных. Полная сборка frontend сначала прошла; последующая проверка TypeScript обнаружила отсутствующие страницы `FinanceOverviewPage`, `FinanceCalendarPage`, `FinanceDebtorsPage`, `FinanceChangesPage`, `FinanceIncomingPage`, `FinanceContractsPage`, на которые продолжал ссылаться `App.tsx`. Эти финансовые страницы менялись в рабочей папке во время выполнения задачи; изменения TrustMe их не редактируют.
