# Релиз: финансы, TrustMe и акты

## Поведение

У финансового договора есть вкладка «Документы и акты». Документы TrustMe сопоставляются явно, только с договором того же студента. Несопоставленные документы видны отдельно. Финансист просматривает и скачивает; админ, МЗК и Академхэлп назначают связи и составляют акты. Перенос и удаление связи с готовыми актами запрещены; исходное сопоставление старого документа допускается и протоколируется.

Миграции 126–130 добавляют финансовую роль, графики, журнал изменений, TrustMe, акты, связь с финансовым договором и очередь финансовых писем. Они не пересчитывают существующие денежные значения. Пользователи не получают финансовую роль автоматически.

## Доставка писем

`FINANCE_EMAIL_NOTIFICATIONS=false` по умолчанию. Настройте SMTP в серверном `.env`, пересоздайте backend и worker, проверьте внутренний адрес скриптом `mail_check.py`. Затем включите флаг явно. Финансовые уведомления на почту получают только активные пользователи с ролью `finance_manager`; пока таких пользователей нет, колокольчик финансовых изменений получает администратор.

Очередь сохраняет отдельное письмо каждому получателю и уникальные пары «событие/получатель». Собственные изменения исключаются из конкретного письма, чужие сохраняются. Состояние `sending` фиксируется до SMTP. Однозначные временные отказы повторяются через 60, 120, 240, 480 и далее 900 секунд, максимум 24 часа. Неопределённый результат и прерванная отправка после пяти минут требуют ручной проверки в разделе «Проверка финансов → Доставка финансовых писем». Статус `sent` означает принятие SMTP. Повторная попытка после ручной проверки открывает новое окно 24 часа и записывается в аудит. Гарантия exactly-once для SMTP не заявляется.

События старше 24 часов автоматически в очередь не попадают. Старое поле `emailed_at` теперь означает, что событие обработано очередью; реальные результаты находятся в журнале по получателям.

## Выкладка

Пуш в main запускает GitHub Actions. Сначала обязательны lint, тесты, сборка, проверка схемы и финансовые E2E на одноразовой БД. Перед merge проверить готовность сервера. Workflow сохраняет предыдущий SHA в журнале, собирает только backend/worker/frontend, снимает бэкап, сохраняет frontend assets, останавливает старый worker, обновляет backend и frontend без пересоздания зависимостей и ждёт готовности. Миграции выполняет backend. После готовности запускается новый worker, проверяются внутренние порты и публичный health.

На уже существующем PROD PostgreSQL, Redis и MinIO остаются прежними. Это процедура обновления работающего сервера; первоначальная установка инфраструктуры описана отдельно в docs/SETUP.md.

Перед откатом остановить worker. Вернуть предыдущие образы/ревизию приложения, совместимые с расширенной схемой. Новые таблицы и PDF не удалять. Полный restore БД допускается лишь при повреждении данных с учётом записей после бэкапа; автоматического destructive downgrade нет.

## Отчёт сопоставления

Без настроенного TrustMe можно получить локальную инвентаризацию:

```sh
docker exec tte_backend_prod python -m scripts.sync_trustme --local-only --limit 1000 --output /tmp/trustme-local-report.json
```

Она не означает, что договоров нет в TrustMe: `incomplete_or_error` с пояснением означает, что внешний поиск не выполнялся. После настройки `TRUSTME_LOGIN`, `TRUSTME_PASSWORD`, `TRUSTME_COMPANY_ID` запустить отчёт с другим именем без `--local-only`. Проверить реальную компанию и доступ с сервера. Отчёты содержат персональные данные и не коммитятся. Подтверждённые совпадения назначаются через интерфейс с аудитом; массовой автоматической привязки по ФИО нет.
