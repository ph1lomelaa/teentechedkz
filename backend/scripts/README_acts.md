# Договоры и акты

Реестр: `/acts` в CRM, `/workspace/acts` в кабинете сотрудников. Последняя вкладка карточки студента — «Акты». Создание доступно admin, mzk_manager, academic_head; ментор видит готовые акты назначенных активных студентов. Студент получает только явно опубликованные PDF.

## Запуск

1. Установить зависимости из `backend/requirements.txt`, собрать frontend (`npm run build`). Шрифты поставляются в `app/assets/fonts` вместе с лицензией.
2. Применить `alembic upgrade head`: зависимости — миграции 127 (TrustMe) и 128 (акты). Настроить доступное файловое хранилище MinIO.
3. Настроить TrustMe по `README_trustme.md`. Перед генерацией сервер проверяет актуальный статус подписанного договора. Номер, ФИО, стороны и фактические услуги необходимо сверить с договором в форме; извлечение текста PDF даёт подсказки, а не юридическую верификацию.
4. Подключить корпоративный почтовый аккаунт через существующие настройки SMTP: `SMTP_HOST`, `SMTP_PORT`, `SMTP_STARTTLS`/`SMTP_USE_SSL`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, при необходимости `SMTP_REPLY_TO`. Секреты хранятся в окружении сервера. Для Google Workspace администратор должен предоставить разрешённый организацией способ SMTP-доступа. OAuth-подключение через интерфейс не реализовано.
5. После настройки проверить письмо на внутреннем тестовом получателе. Статус «отправлено» означает принятие SMTP-сервером, а не доставку адресату. Неопределённый результат блокирует повторную отправку до ручной проверки папки отправленных; действие проверки протоколируется.

## Сверка TrustMe на PROD

Запустить из backend: `python -m scripts.sync_trustme --output /secure/path/trustme-report.json --limit 100`. Скрипт формирует отчёт без автоматической привязки: уже привязаны / один кандидат / несколько / неподписанные / не найдены / неполный поиск или ошибка. Поддерживает `--resume` и повторяемый `--student-id`. Сопоставления требуют проверки перед привязкой. Отчёт содержит персональные данные, не публиковать его в репозитории.

## Проверка 2026-11-01

Локально выполнены тесты схем, PDF (включая казахские буквы и денежные значения), ролей, неизменяемости готовых документов, доступа студента, очистки хранилища при ошибке БД, идемпотентности отправки и обработки неопределённого результата. Проверены компоненты формы и навигация; production-сборка frontend проходит.

Дополнительно выполнены финансовые API-сценарии на одноразовой PostgreSQL, проверка восстановления копии PROD и миграций 125→130 с контролем сохранности финансов. Реальные письма не отправлялись: SMTP и TrustMe пользователь настроит на сервере позднее. Результаты и порядок релиза описаны в README_release_finance.md. Проверка в живом браузере ограничена недоступностью browser host.
